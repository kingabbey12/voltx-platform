# Object Storage (Cloudflare R2)

The API verifies object storage at boot (`S3StorageProvider.verifyProductionReadiness`) and **refuses to start** if the bucket is unreachable. That guard is deliberate: attachments silently failing in production is worse than a loud refusal. Do not weaken it.

## Current status

**BLOCKED.** The configured credentials return **HTTP 401** on `HeadBucket`. The endpoint resolves and is reachable (an unauthenticated root GET returns 400, as expected), so this is authorization — a revoked or invalid token — not networking.

## Rotation (owner action)

Requires Cloudflare dashboard access. No part of this can be automated from the repository.

1. Cloudflare → **R2** → select the account and bucket.
2. Create a **scoped** API token. Not an account-wide admin token.
3. Grant the minimum the application needs:
   - Read objects
   - Write objects
   - Delete objects — only because attachment deletion exists
   - Bucket metadata/list — only if required
4. Scope the token to the single bucket named by `ATTACHMENTS_S3_BUCKET`.
5. Write the values into `deploy/.env` (mode **600**, gitignored) or the approved secret store.
6. Verify (below).
7. **Revoke the old token** once verification passes.

## Variables

The repository's actual names — note the `ATTACHMENTS_` prefix, not a bare `S3_`:

| Variable | Purpose |
| --- | --- |
| `ATTACHMENTS_STORAGE_PROVIDER` | `s3` in production; `local` is rejected there |
| `ATTACHMENTS_S3_BUCKET` | bucket the boot check probes |
| `ATTACHMENTS_S3_REGION` | `auto` for R2 |
| `ATTACHMENTS_S3_ENDPOINT` | `https://<account-id>.r2.cloudflarestorage.com` |
| `ATTACHMENTS_S3_ACCESS_KEY_ID` | credential |
| `ATTACHMENTS_S3_SECRET_ACCESS_KEY` | credential |
| `ATTACHMENTS_S3_FORCE_PATH_STYLE` | `false` for R2 |

## Verification

Use the application's own SDK configuration. Round-trip a disposable object under `release-verification/<timestamp>/r2-healthcheck.txt` and delete it afterward.

```
HeadBucket → upload → read → delete → API readiness
```

Then confirm the API boots and `/readiness` returns 200 — that is the only check that proves the *application's* view of storage, not just the SDK's.

Never print credential values, and never place them in this file.

## Troubleshooting

| Symptom | Meaning |
| --- | --- |
| `HeadBucket` 401 | token revoked, wrong account, or wrong secret |
| `HeadBucket` 403 | token valid but not scoped to this bucket |
| `HeadBucket` 404 | bucket does not exist in this account |
| API logs `Cannot reach S3 bucket` | any of the above — the API is refusing to start, as designed |
